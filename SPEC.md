# SZGC

Код: `szgc_core.py` (таблицы и загрузчик модели), `szgc_codec.py`
(кодер/декодер), `web/szgc.js` (порт на JavaScript), `rust/` (порт на Rust).

## 1. Коротко

SZGC сжимает текст не байтами, а **токенами**: слово, знак пунктуации, литерал (всё прочее). Для слова кодек сначала пытается угадать его из контекста — по двум предыдущим словам, по предыдущему слову, по лемме, по пунктуации. Если угадал, слово стоит доли бита. Если нет — слово записывается своим номером в
словаре (рангом), а не буквами. Всё как в LM-подходах (почти).

Всё, что удалось «угадать» и «пронумеровать», упаковывается обычным арифметическим (range) кодером. Словарь и статистика лежат в отдельном файле модели, поэтому в сжатом сообщении лишних и избыточных служебных данных почти нет.

| Термин | Что значит здесь |
|---|---|
| **токен** | единица текста: слово, знак пунктуации или литерал |
| **словоформа** | конкретная форма слова («пошли», «пошла», «пошёл» — три разные) |
| **ранг** | номер словоформы в словаре модели; частые слова имеют малые ранги |
| **контекст** | то, по чему кодек угадывает: предыдущие слова, лемма, знак |
| **таблица** | набор «символ — вес (частота)» для одного контекста |
| **escape** | сигнал выхода «этого символа в таблице нет»; после него ищут в следующей |
| **исключение (exclusion)** | символы, уже исключённые верхней таблицей, чтобы не платить за них дважды |
| **range-кодер** | арифметический кодер: превращает последовательность (символ, вероятность) в биты |

## 2. Контейнер потока

Сжатый файл — это один байт тега и дальше полезная нагрузка:

```
[tag][payload]

tag = 0x02   токенный режим (словарь + контексты) — основной
tag = 0x03   байтовый режим: контексты order-3 + order-2 + order-0
tag = 0x04   байтовый режим: order-2 + order-0
tag = 0x05   байтовый режим: order-0
```

Кодер всегда считает все четыре варианта и записывает самый короткий. Тег
занимает ровно один байт и не кодируется — декодер узнаёт режим сразу. Поэтому
на случайном мусоре кодек не раздувается: он честно выбирает байтовый режим.

Ни версии, ни длины, ни контрольной суммы в заголовке нет: длина потока
известна из файла, а конец токенного потока помечен символом EOS (см. ниже).

## 3. Токенный режим (tag 0x02)

### 3.1. Разбиение на токены

`tokenize()` режет строку на чередование: слово (`[А-Яа-яЁёA-Za-z]+`),
литерал (всё, что между словами). Литерал, совпавший с одной из 48 записей
таблицы пунктуации (`" "`, `", "`, `". "`, `"! "`, `" — "` и т. п.), кодируется
как пунктуация, иначе — как литерал.

### 3.2. Что пишется для каждого токена

Сначала адаптивная таблица `kind` пишет тип токена:

| kind | значение |
|---:|---|
| 0 | слово из словаря |
| 1 | знак пунктуации из таблицы |
| 2 | литерал длиной в 1 байт |
| 3 | конец потока (EOS) |
| 4 | литерал длиной больше 1 байта |

Отдельного счётчика токенов нет — декодер читает типы, пока не встретит тип №3.

**Слово (тип 0).** Дальше идёт одна из двух дорог:

1. **LZP.** Если пара двух предыдущих слов уже встречалась, кодек пишет флаг «продолжение то же» (адаптивная таблица из двух символов) и, при попадании, только флаг регистра. На повторяющихся фразах слово стоит около одного бита.
2. **Словарная цепочка или сырые байты.** Кодек целочисленно оценивает оба
   варианта (в битах, без плавающей точки) и выбирает дешёвый:
   - *сырые байты*: флаг пути + байт (или литерал) — выгодно для имён,
     опечаток, ссылок;
   - *словарная цепочка*: таблицы по порядку
     `MATCH → O2 (пара слов) → B1 (предыдущее слово) → C (контекст знака)` →
     `LEM (лемма предыдущего слова)` → `O0 (частота слова)` → `ESC_RANK`
     (номер ранга через varint).

   На каждом шаге работает PPM-механика: если таблица не содержит символ, она
   пишет escape, а её символы добавляются в список исключений для нижних таблиц.

В конце слова — флаг регистра (0 строчные, 1 с заглавной, 2 ЗАГЛАВНЫЕ,
3 смешанный). Смешанный регистр не словарный: такое слово уходит в сырые байты.

**Пунктуация (тип 1).** Флаг пути: 0 — сырой байт, 1 — по таблице, 2 — сырой литерал. По таблице: `A` (какой знак обычно идёт после  (какой знак идёт после этого знака), затем `O0` как запасной вариант.

**Литерал (типы 2/4).** Однобайтовые литералы пишутся прямо байтом. Длинные — через модель длин (64 веса) и байтовый контекст: `byte1` (16 вариантов после предыдущего байта) и `byte0` (256 весов).

### 3.3. Пример

Текст `Привет! Как дела?` (6 токенов: слово, «! », слово, « », слово, «?»):

```
тип 0 (слово)  → LZP-флага нет (начало текста)
                → «привет» есть в словаре? да → цепочка таблиц
                → B1/LEM/O0: ранг слова «привет», case-флаг 1 (с заглавной)
тип 1 (пункт.) → «! » в таблице 48 → таблица C/A → O0
тип 0 (слово)  → «как» по B1 от предыдущего слова
тип 1          → « » — самый частый знак, один-два бита
тип 0          → «дела» по B1
тип 1          → «?» по таблице A после слова «дела»
тип 3          → EOS
```

Итог — 13 байт вместе с тегом. Ни слова, ни знаки не записаны буквами.

## 4. Байтовые режимы (tag 0x03–0x05)

Работают без словаря: varint(длина в байтах) и дальше каждый байт кодируется адаптивной таблицей своего контекста. Глубина контекста задаётся тегом: order-3+order-2+order-0, order-2+order-0, только order-0. Это страховка для текста, который не является языком: Base64, случайные символы, мусор.

## 5. Файл модели (`graph-model.bin`)

```
"SZGM" + 0x02                       заголовок и версия формата
varint D, P, L, O0_TOP, B1_ROWS, B2_ROWS, LEM_ROWS
P × blob                            записи таблицы пунктуации (UTF-8)
D × blob                            словоформы, индекс = ранг
D × varint                          id леммы для каждой словоформы
order-0: n, (sym, weight) × n, esc_rank, esc_lit
B1:  n, [key, k, (sym, weight) × k] × n
B2:  n, [pair, k, (sym, weight) × k] × n
LEM: n, [lemma_id, k, (sym, weight) × k] × n
A:   n, [word_sym, k, (sym, weight) × k] × n
C:   n, [punct_idx, k, (sym, weight) × k] × n
byte0: 256 × varint                 веса для order-0 по байтам
byte1: n, [prev_byte, k, (sym, weight) × k] × n
case:  4 × 3 × varint               регистр по 4 контекстам
len:   64 × varint                  модель длин литералов
```

`blob` — это varint длины, затем байты. Порядок символов внутри строки — по возрастанию `sym` (фиксирован, чтобы файл был воспроизводим).

Размеры текущей модели (`model-stats.json`): D = 600 000 словоформ, P = 48 знаков, L = 264 054 леммы, O0_TOP = 65 536, до 65 536 строк `B1` и `B2`, до 16 384 строк `LEM`, до 14 продолжений в строке `B1`, 9 в `B2`, 12 в `LEM`, 4 в `A`, 8 в `C`, 16 в `byte1`. Файл целиком — 18 748 852 байта (17,9 МиБ).

Обучение — `build_model.py` (три прохода по корпусу) и
`train_colab.ipynb`.

## 6. Детерминизм

Требование: один и тот же текст в Python, JavaScript и Rust должен дать одинаковые байты, иначе файл, сжатый в браузере, не прочитается на сервере.

- Только целые числа. Нет ни одного `float` ни в кодеке, ни в модели, ни в декодере; сравнение «цепочка или сырые байты» считается в целых битах.
- Range-кодер 32-битный: `low`/`range`, кэш-байт и переносы (как в LZMA). Декодер вычитает `cum` из `code` (как в PPMd).
- Порядок перечисления таблиц и символов задан форматом файла, а не порядком в памяти или хэшем.
- JavaScript не умеет оперировать 64-битнымие целыми, поэтому пара слов собирается умножением `w2 * 2097152 + w1` (а не сдвигом), а все промежуточные значения держатся ниже 2^53 — так double-тип остаётся точным.
- Состояние сбрасывается между вызовами: адаптация за время одного `compress`/`decompress` откатывается по списку затронутых таблиц (touched-set), поэтому сообщения не влияют друг на друга (защита от загрязнения данных).

Проверяется тестами: `tests/vectors.json` (36 пар «текст → hex»),
`tests/szgc_crosscheck.js`, `tests/rust_crosscheck.py` (150 текстов в обе стороны), `tests/fuzz.py` и `tests/jsfuzz.js`.

## 8. Ограничения

- **Английский текст проигрывает brotli (пока что)** на длинных статьях (в бенчмарке `en_quantum` +529 Б, `en_2026` +380 Б). Причина в словаре: 600 000 словоформ в основном русские. Лечится переобучением на данных с дополненным англоязычным корпусом.
- **Скорость кодирования** около 8 КБ/с в Python, 15 КБ/с в JS, 35 КБ/с в Rust. На сообщении в 30–60 байт это 1–5 мс, на статье в 6 КБ — 0,2–0,7 с. Для многомегабайтных файлов кодек пока не годится: там нужен zstd или xz.
- **Формат не расширяется без потери совместимости!!!** Любое изменение потока требует либо новой версии тега, либо новых эталонных векторов; сейчас векторы — единственный контракт между реализациями. Перед обновлением тщательно просмотреть архитектуру на возможность добавления полноценной системы обратной совместимости и управления моделями сжатия «на лету».
